# P2 macOS 性能调查

## 状态和证据边界

本次环境为 Apple M2 Pro、32 GB，Godot 4.7.2；系统显示信息未列出可用显示器。Headless 运行没有 Metal 图形测量，不能代表目标 M2 / 16 GB，也不能用于判断全屏 FPS。尚未完成独立 Release 的 60 秒窗口/全屏矩阵、Retina 五档缩放或各系统 A/B。本次没有基于不完整证据修改正式画质或物理。

## 现有历史基线

仓库 [PERFORMANCE_REPORT.md](PERFORMANCE_REPORT.md) 记录了同一 M2 Pro 的历史 Forward+ / Metal 短时测试：3440×1440 窗口、画质优先、云开约 60 FPS；外接屏全屏报告输出 6880×2880，画质优先约 16.7–17.0 FPS，性能优先约 20.3 FPS。每组仅 5 秒，场景是 SimpleParticleWake，并非本次 Main 的 60 秒验收。全屏屏幕输出像素是窗口的四倍，这是额外像素压力的重要线索，但不能单凭这组不同输出尺寸和质量档确认当前的 GPU 瓶颈。

同一历史报告的全屏云开/关配对中，关闭云层约增加 3–6 FPS；粒子尾流开关的差异没有稳定超过测量噪声。FSR2 的 0.75 档在部分短测中并不比 1.0 快，可能涉及上采样和其他负载，仍需在固定条件下复测。没有可靠 GPU 毫秒，以上帧时间均为完整帧间隔，不是 GPU 时间。

用户观察到的窗口约 60→30 FPS 没有同分辨率、同版本设置和同场景的前后对照，因此无法归因到具体提交。近期 `c7753ea` 增加帆面着色和卷帆视觉，是可测候选，并非已确认的回归来源。`3ef435b` 增加 Polar UI，是否关闭时带来成本需要实际测量。应比较相邻版本的独立构建，固定设置和船只类型后再定位。

## 现有结构与可能成本

- `QualityManager` 已提供 1.00、0.75、0.67 的 3D 缩放档，低于 1 使用 FSR2；内部尺寸在现有 HUD 中明确标为估算。当前没有直接提供本任务要求的 0.85、0.65、0.50 独立诊断档。
- 帧率选项中 30 FPS 档设置 `Engine.max_fps=30` 且关闭 VSync；60 FPS 档为上限 60、VSync 开；无限档上限 0、VSync 关。测试必须记录档位，否则 30 FPS 读数可能是人为限制。
- `shaders/sea_water.gdshader` 包含顶点波浪及法线循环、三平面纹理、屏幕纹理采样和泡沫等；海面 `addons/boujie_water_shader/types/ocean.gd` 构建分层 LOD 网格。存在潜在顶点、像素和屏幕采样成本，但本轮未单独隔离，不能排序为最大瓶颈。
- 海面几何在构建和 LOD 更新时生成；本次没有证据表明它每帧重建。历史结果中的云层成本和异常输出像素数值得优先复核，阴影、港口几何、天气粒子及 CPU 采样均未完成本轮独立 A/B。

## 本轮改动与验证

扩展 `scripts/boat_hud.gd` 的现有 F3 性能区：打开面板后，按系统单调时钟收集 60 秒帧间隔，结束时计算帧数/真实耗时得到的平均 FPS、平均帧间隔及 P95，同时显示渲染图元计数。关闭再打开 F3 会重置采样。采样包括 VSync、调度和资源加载等待；它不是 GPU 时间。F3 自身可影响性能，应在后续对照中保持同样状态。没有更改船舶、波浪、天气或画质配置。

`godot --headless --path . --editor --quit` 退出码 0；`git diff --check` 通过。`tests/test_day_night_cycle.gd` 退出码 1，报告 17 项关于太阳、水色和昼夜质量档的断言失败；本轮尚未判定其原因为旧测试、Headless 环境还是其他变化，不能宣称天气回归通过。Headless 还有 RendererDummy 退出资源提示及已有 translation UID 警告。

## 目标设备复测步骤

1. 在目标 Mac 上运行独立 Release，预热并固定船位、镜头、时间、天气、风浪与船状态；记录机型、屏幕模式、电源模式、Godot 版本、帧率上限和 VSync。
2. 窗口/全屏各打开 F3，记录窗口、屏幕、Viewport 和估算内部尺寸、画质档、Draw Calls、可见物体、图元、CPU process 时间。打开 F3 后保持 60 秒，记录平均 FPS、平均帧时及 P95；重复至少三轮并记录卡顿。切换配置后关闭再打开 F3 重置采样。
3. 按开阔海域晴天/夜晚、港口晴天/夜晚、恶劣天气完成窗口和全屏矩阵。不要把窗口和全屏不同画面、天气或分辨率直接比较。
4. 先用现有 1.00 / 0.75 / 0.67 档做初筛；这些档也改变阴影、SSR、云等质量，不能当作单变量分辨率实验。0.85 / 0.65 / 0.50 及严格单变量缩放仍需要独立诊断入口；保持其他渲染设置固定，在 Release 构建测足 60 秒并检查 FSR2 画质。
5. 在固定输出和质量下，分别做云、海面片元、海面顶点、反射/额外 pass、CPU WaveSampler、阴影和港口对象的单项 A/B。波浪物理保持运行。用 Xcode Instruments 的 Metal System Trace 获取 GPU 队列与 pass 时间，与 CPU 帧间隔对照；不要以 1000/FPS 充当 GPU 毫秒。

## 结论与下一步

- 全屏稳定 30 FPS：**尚未验证**。当前距目标多少无法计算；历史短测为约 16–24 FPS，不能替代当前目标设备的 60 秒结果。
- 窗口下降原因：**尚未定位**；没有证据将它归因于某一提交。
- 最大瓶颈：**未确定**。已有证据优先指向全屏输出像素数及云层成本，不能排除 CPU、其他 GPU pass 或同步等待。
- 40–45 FPS：有待目标机真实基线、单项 A/B 和 Metal trace；不能保证达到。
- 下一项：先在目标机验证全屏实际输出像素、帧率限制和 60 秒 P95，再做固定质量的分辨率缩放与云层 A/B。仅在得到可重复的收益和画质对照后实施单项优化。

回滚本轮诊断只需撤销 `scripts/boat_hud.gd` 中的帧时间采样和性能标签修改；本报告可独立保留。没有实施可声称提升 FPS 的优化，尚无优化前后性能或画质对比。
